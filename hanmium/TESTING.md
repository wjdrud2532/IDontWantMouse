# Hanmium 테스트 기록

지금까지 한 테스트와 결과, 다시 확인하는 방법을 모았습니다. 날짜는 모두 2026-11-04입니다.

- **확인됨:** 실제로 돌려서 결과를 봤습니다.
- **간접 확인:** 같은 코드를 창 없이 그리거나 값만 출력해서 봤고, 실제 화면 조작은 하지 않았습니다.
- **미확인:** 빌드만 했습니다.

## 1. 스크롤 전달 (휠 이벤트)

| 테스트 | 방법 | 결과 |
|---|---|---|
| 커서를 옮기지 않고 창에 직접 휠 보내기 | `postToPid` + 필드 51(창 번호) + `CGEventSetWindowLocation`으로 앱마다 스크롤 | 확인됨: Chrome, Safari, VS Code, Slack, Notion, Finder, Pages, WezTerm. 필드 51 없이 `postToPid`만 쓰면 스크롤되지 않음 |
| WezTerm 휠 동작 측정 | `less`를 띄운 시험 패널에서 `wezterm cli get-text`를 반복해 줄 이동량 확인 | 확인됨: 정밀 휠은 15px당 1줄, 전체 화면 앱에서는 크기와 상관없이 이벤트 1개가 1칸 → 칸 단위로 묶어 보내도록 수정. `get-text`는 스크롤백 위치를 반영하지 않음 |

## 2. 권한과 실행

| 테스트 | 방법 | 결과 |
|---|---|---|
| 다시 빌드해도 손쉬운 사용 권한 유지 | 고정 서명 인증서로 빌드 → 재실행 → 메뉴 막대 아이콘 툴팁을 AX로 읽기 | 확인됨: "Hanmium 실행 중" 유지 |
| 화면 기록 권한 상태 | 툴팁에 권한 경고가 붙는지 확인 | 확인됨: 권한 있음, 굴절 적용 중 |
| TCC DB 직접 조회 | `sqlite3`로 TCC.db 읽기 | 실패: 접근 거부 → 툴팁으로 확인하는 방식으로 바꿈 |
| 비정상 종료 여부 | `~/Library/Logs/DiagnosticReports`, 실행 시각 확인 | 확인됨: 기록 없음 |
| 단일 실행 | 새로 실행하면 이전 Hanmium이 종료되는지 | 확인됨: `pgrep`으로 1개만 남음 |

## 3. 유리 라벨 (리퀴드 글래스)

화면 구석에 키 포커스를 받지 않는 시험 패널을 1초 띄우고 `screencapture`로 찍었습니다(시험 도구 ①).

| 테스트 | 결과 |
|---|---|
| 흐림 재질 유리 (첫 버전) | 확인됨, 그 뒤 버림: 재질이 거의 불투명해서 뒤 색이 비치지 않음 |
| 시스템 `NSGlassEffectView` (.clear / .regular) | 확인됨, 쓰지 않기로 함: 라벨 크기(약 20px)에서는 굴절이 보이지 않고 흐림만 있음. 어두운 배경에서 글자가 탁함 |
| 화면 캡처 + 직접 굴절 계산 (kube.io 모델) | 확인됨: 주황·보라 원 위에서 가장자리 굴절, 어두운 배경에서 글자색이 자동으로 흰색. 라벨 16개 그리는 데 5ms |
| 굴절 강화 전후 비교 | 확인됨: 처음에는 흐린 화면을 굴절시켜서 차이가 안 보였음. 가장자리에 선명한 화면을 쓰도록 고친 뒤 테두리가 또렷해짐 |
| 설정 미리보기 (기본값 / 굴절 200%·반사 200%·흐림 0) | 간접 확인: `ImageRenderer`로 렌더링, 슬라이더 값 차이가 그림에 반영됨 |

| 측정 | 결과 |

| 테스트 | 방법 | 결과 |
|---|---|---|
| 고르지 않은 영역: 점선 + 옅은 칠 | 시험 도구 ① | 확인됨 |

## 6. 스크롤 영역 찾기

| 테스트 | 방법 | 결과 |
|---|---|---|
| WezTerm 분할 창 위치 | `screencapture -l <창 번호>`(가려진 창도 찍힘) 위에 계산한 사각형을 그려 비교 | 확인됨: 처음에 세로로 5–10px 어긋남 (여백을 위아래 반씩으로 가정한 탓) → `~/.wezterm.lua`의 `window_padding`을 읽게 고쳐서 일치 |
| WezTerm AX 창 번호 = CG 창 번호 | `_AXUIElementGetWindow`와 `CGWindowListCopyWindowInfo` 비교 | 확인됨: 같음 |
| Slack 스크롤 영역 | AX 트리 탐색 | 확인됨: 창 전체 틀 하나만 노출, 스크롤 관련 AX 속성 없음 → 공통 규칙(스크롤 막대 / 목록 역할 / 이름에 'scroll')으로 채널 목록·메시지·스레드 3개를 찾게 됨 |
| 공통 규칙을 여러 앱에 적용 | `--dump` | 확인됨: Slack 3개, VS Code 3개, Chrome(HN) 1개, WezTerm 4개 |
| 빈 환경에서 `wezterm cli` 연결 | `env -i HOME=… wezterm cli list` | 확인됨: 메뉴 막대에서 실행된 Hanmium도 연결됨 |
| 새 WezTerm 창의 분할 창 | 시험 창 + `--dump` | 처음에 실패: 새 창의 CLI 창 제목이 빈 문자열이라 제목으로 짝을 못 지음 → 창 크기로 짝짓게 고친 뒤 확인됨 |

## 7. 스크롤 모드 동작 (실제 키 입력으로 재현)

분할 창이 2개인 시험용 WezTerm 창을 따로 띄워, 앞 창을 확인한 뒤 `osascript`로 키를 보내고 로그와 화면을 확인했습니다(시험 도구 ②).

| 시나리오 | 결과 |
|---|---|
| 처음 열기 | 확인됨: 분할 창 2개를 찾고 활성 창에서 시작 |
| Tab → Enter → 다시 열기 | 확인됨: Enter로 고른 창이 실제로 활성이 되고, 다시 열면 그 창에서 시작. 고치기 전에는 창 전체에서 시작 |
| Shift-Tab → Esc → 다시 열기 | 확인됨: 포커스가 그대로면 마지막으로 쓰던 창에서 시작 |

## 9. 성능 측정과 최적화

`HANMIUM_PROFILE=1 .build/release/Hanmium --dump <번들ID>`를 실행하면 단계별 시간이 나옵니다.

| 측정 | 결과 |
|---|---|
| 라벨 찾기 단계별 (WezTerm·Finder·Slack) | 메뉴 막대 상태 아이콘 찾기가 200–275ms로 전체(250–380ms)의 70–85%. 창 안 훑기는 1–35ms. 실행 중인 46개 앱마다 상태 아이콘을 묻고, 응답이 늦은 앱을 제한 시간(150ms)까지 기다림 (아직 고치지 않음) |
| `wezterm cli list` / `list-clients` | 10–30ms, 문제없음 |
| 화면 사진 변환 (1920×1080) | 7.6ms |
| 유리 라벨 250개 | CPU 122.7ms → **GPU 4.5ms** (첫 실행 9ms) |
| 큰 영역 유리 막대 | CPU 30–69ms (1100×800) → GPU 1ms 안팎 |
| GPU와 CPU 모습 비교 | 같은 배경에 나란히 그려 확인: 라벨과 막대가 거의 같음 |
| 물방울 이동 중 뒤 화면 | 한 장씩 찍기(창 목록 + 캡처 40–60ms) → 연속 캡처(SCStream, 초당 최대 30장, 백그라운드에서 변환) |

### 라벨이 뜨기까지 걸리는 시간 (실제 앱, 단축키 → 라벨이 다 그려짐)

`~/Library/Logs/Hanmium.log`의 "라벨 모드" 줄로 잽니다. 단계별 시간은 `defaults write com.local.Hanmium profile -bool true`로 켭니다(재고 나서 `defaults delete com.local.Hanmium profile`).

| 측정 (WezTerm 시험 창, 대상 53개) | 이전 | 최적화 뒤 |
|---|---|---|
| 상태 아이콘 찾기 | 175–248ms | 20–22ms |
| WezTerm 분할 창 (`wezterm cli` 2번) | 82–106ms | 1–13ms |
| 단축키 → 대상 찾기 끝 | 105–226ms | 61–69ms |
| 단축키 → 라벨이 다 그려짐 | 144–300ms | 74–82ms (앱 시작 뒤 첫 회 172ms) |

- **상태 아이콘:** 실행 중인 49개 앱 중 상태 아이콘이 있는 앱은 10개뿐이었습니다. 앱마다 답하는 데 30–60ms가 걸려 매번 다 묻느라 느렸는데, 이제 아이콘이 있는 앱만 기억해 두고 묻습니다(`ExtrasCache`). 전체 목록은 앱 시작 때와 1분에 한 번 뒤에서 새로 고칩니다. 대상 수는 53개로 그대로입니다.
- **WezTerm:** `wezterm cli` 두 번을 창 훑기와 동시에 돌립니다(`WezTerm.Prefetch`).
- **미리 준비:** GPU 셰이더는 앱 시작 때 컴파일하고, 화면 사진을 GPU로 올리는 일은 캡처 직후 백그라운드에서 합니다.

## 12. 고르지 않은 창 테두리 색

시험용 WezTerm 창에서 스크롤 모드를 열기 전과 연 뒤의 같은 자리 색을 비교했습니다.

| 자리 | 열기 전 | 고치기 전 (모드 중) | 고친 뒤 (모드 중) |
|---|---|---|---|
| 고르지 않은 창 안 | #222432 | #2E3E64 (파랗게) | #1B1D28 (색조 그대로, 조금 어둡게) |
| 고르지 않은 창 가장자리 | #2F3342 | #697EAA (연보라) | #6F7386 (회색 빛) |
| 고른 창 안 | #1B3D26 | #1B3D26 | #1B3D26 |

- **원인:** 파란 강조색 20% 덮기 + 가장자리 채도 1.4배 + 흰 빛이 WezTerm 남색 배경과 섞여 연보라가 됐습니다. WezTerm 쪽 색은 바뀌지 않았습니다.
- **수정:** 고르지 않은 창은 색 덮기와 채도 보정 없이 굴절과 흰 빛만 남겼습니다. 굴절 가장자리는 그 창이 고르지 않은 창이 될 때의 화면으로 한 번만 그리고, 물방울 이동 중에도 걷었다 덮었다 하지 않습니다.

### 보라색 테두리의 진짜 원인 (자기 자신을 다시 찍음)

| 확인 | 결과 |
|---|---|
| 어두운 분할 창을 고른 뒤 그 테두리 | #9550F8 (보라) — 사용자 스크린샷의 #A336F8과 같은 현상 |
| 같은 순간 WezTerm 창만 찍기 (`screencapture -l`) | 그 자리는 WezTerm 노란 분할선 #FEFC78 → 보라색은 Hanmium 오버레이가 만든 것 |
| 같은 배경으로 GPU·CPU, RGBA·BGRA 네 조합 계산 | 모두 연두 #C4DF91 → 계산식 문제 아님 |
| 시간에 따른 색 (0.5~3초) | #8D58F8 → #9452F8로 변한 뒤 고정 → 쌓이는 현상 |
| 로그 "연속 캡처 시작" | 뺄 오버레이 창 [21260]을 화면 목록에서 찾지 못함 |

- **원인:** 연속 캡처를 막 띄운 오버레이 직후에 시작해서, 화면 목록에 아직 오버레이 창도 Hanmium 앱도 없었습니다. 그래서 오버레이를 빼지 못하고 자기 자신을 찍었고, 유리가 자기 자신을 다시 굴절시키며 파란 덮기와 채도 1.4배가 쌓여 보라색으로 수렴했습니다.
- **수정:** 화면 목록을 보이지 않는 창까지 포함해 받고, 창 번호가 아니라 **Hanmium 앱 단위로** 뺍니다. 그래도 못 찾으면 찍지 않고 0.2초 뒤 다시 시도합니다.
- **고친 뒤:** 로그 "앱 단위", 분할선 자리 #A3CE7C(연두, 계산값과 같음), 0.5~3초 동안 색 변화 없음.

## 13. 아직 확인하지 않은 것

- **스크롤 모드 Enter의 일반 앱 경로:** 링크·버튼이 아닌 자리를 찾아 누르기. VS Code, Slack 등에서 실제로 눌러 보지 않음 (WezTerm 경로만 확인).
- **물방울 이동 중 실시간 굴절:** 이동하는 동안 계속 다시 캡처. 실제 화면에서 보지 않음.
- **설정 창 전체:** 유리 슬라이더, 미리보기, 모양·영역 이동 선택, 영역 이동 속도, 터미널 휠 줄 수 입력란, 앱별 사용, 테두리 색, 기본값 복원, 내보내기·가져오기 버튼. 설정 창을 열어 보지 않음.
- **메뉴 막대 "앱 점검…" 결과 창:** 점검 내용은 `--check`로 확인했지만, 결과 창은 띄워 보지 않음.
- **물방울 이동 중 연속 캡처로 바뀌는 굴절:** 실제 움직임을 눈으로 보지 않음.
- **GPU를 쓸 수 없을 때 CPU로 돌아가는 경로:** 이 Mac에는 GPU가 있어서 확인하지 않음.
- **실제 라벨 모드의 유리 라벨:** 라벨이 수백 개일 때 처음 그리는 속도. 라벨 하나에 0.3ms로 추정.
- **화면 환경:** 여러 모니터, Retina 화면(이 Mac은 1920×1080, 1배).
- **WezTerm 탭이 여러 개인 창:** 탭 바 높이를 추정에 의존.

## 다시 확인하는 방법

**회귀 테스트 (`Tools/`)**

```sh
Tools/check-apps.sh                       # 실행 중인 앱 전부 점검, 경고 있으면 종료 코드 1
Tools/check-apps.sh com.tinyspeck.slackmacgap com.github.wez.wezterm
Tools/e2e-wezterm.sh                      # 시험용 WezTerm 창에서 Enter·Esc 시나리오 (build.sh 후 앱을 다시 띄워 두고)
```

**값만 출력 (화면에 아무것도 안 뜸)**

```sh
cd ~/Hanmium && swift build -c release
.build/release/Hanmium --dump com.github.wez.wezterm   # 번들 ID를 바꿔 다른 앱
```

라벨 클릭 대상과 스크롤 영역 목록을 출력하고, 포커스가 있는 영역에는 `← 포커스`가 붙습니다.

**예시 앱 (`Demos/`)**

```sh
Demos/build.sh DropletDemo      # 스크롤 모드 물방울 이동 A/B → .build/demos/DropletDemo
Demos/build.sh LinkLabelsDemo   # 링크 많은 페이지 라벨 방식 8가지 → .build/demos/LinkLabelsDemo
```

**동작 로그**

스크롤 모드를 열고 닫을 때와 Enter를 누를 때마다, 찾은 영역·포커스·기억된 영역·시작 영역을 `~/Library/Logs/Hanmium.log`에 남깁니다. 1MB가 넘으면 새로 씁니다.

**시험 도구 ① 화면 구석 시험 패널**

`Sources/Hanmium`에서 `main.swift`만 뺀 파일들에 시험용 `main.swift`를 붙여 `swiftc`로 빌드합니다. 키 포커스를 받지 않는 `.nonactivatingPanel`을 화면 구석에 띄우고, `screencapture -R`로 찍은 뒤 끝냅니다. 터미널(WezTerm)에 화면 기록 권한이 있어서 캡처가 됩니다.

**시험 도구 ② 시험용 WezTerm 창에서 실제 키 입력**

쓰고 있는 창은 건드리지 않습니다. 5초 정도 걸리고, 그동안 키보드를 쓰지 않아야 합니다.

```sh
P1=$(wezterm cli spawn --new-window -- bash -c 'seq 1 3000; exec bash')
P2=$(wezterm cli split-pane --pane-id $P1 --right --percent 30 -- bash -c 'seq 1 3000; exec bash')
wezterm cli activate-pane --pane-id $P1; sleep 1.2
# 앞 창이 시험 창("wezterm-gui, bash")인지 먼저 확인한 다음에만 키를 보낸다
osascript -e 'tell application "System Events" to tell (first process whose frontmost is true) to get {name, value of attribute "AXTitle" of front window}'
osascript -e 'tell application "System Events" to key code 38 using {shift down, command down}'  # ⇧⌘J 열기
osascript -e 'tell application "System Events" to key code 48'                                   # Tab
osascript -e 'tell application "System Events" to key code 36'                                   # Enter
screencapture -x /tmp/hanmium-check.png
wezterm cli kill-pane --pane-id $P2; wezterm cli kill-pane --pane-id $P1
cat ~/Library/Logs/Hanmium.log
```

**가려진 창의 위치 확인**

`screencapture -x -o -l <CG 창 번호>`는 다른 창에 가려진 창도 그 창만 찍습니다. 계산한 영역 사각형을 그 위에 그려 비교합니다.

## 테스트할 때 주의

- **합성 클릭 전 확인:** 누르려는 창이 맨 위인지 같은 명령 안에서 확인합니다. 예전에 잘못된 클릭으로 VS Code에 탭이 열린 적이 있습니다.
- **Claude Code 패널은 스크롤하지 않음:** 휠이 화살표 키로 바뀌어 입력창이 바뀝니다.
- **Esc를 함부로 보내지 않음:** 모드가 실제로 열렸을 때만 보냅니다. 열리지 않았으면 Esc가 사용 중인 앱으로 갑니다.
- **새 창이나 시험 패널은 짧게:** 띄우는 동안 사용자 입력이 그쪽으로 갈 수 있습니다.
