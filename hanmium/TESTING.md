- **영역 찾기를 줄인 것:** 웹 화면 안의 분할 창 찾기와 스크롤 상자 찾기를 동시에 묻고, 창 안을 훑을 때는 역할·위치·크기만 묻는다(영역으로 쓸 것만 속성을 다 받음).
- **해 보고 되돌린 것:** 자식 목록을 같은 호출로 받기. 멈춰야 할 표·목록의 자식(메일 수천 통)까지 받아서 Mail 이 더 느려짐.
- **실제로 걸린 시간:** 이제 로그에 `스크롤 모드 다시 열기: 기다림·확인 … · 영역 찾기 [앱] … · 그리기 끝 …` 으로 남는다. 테두리를 그리는 시간은 실제 화면에서만 잴 수 있어서 아직 숫자가 없음.

## 12. 고르지 않은 창 테두리 색

시험용 WezTerm 창에서 스크롤 모드를 열기 전과 연 뒤의 같은 자리 색을 비교했습니다.

| 자리 | 열기 전 | 고치기 전 (모드 중) | 고친 뒤 (모드 중) |
|---|---|---|---|
| 고르지 않은 창 안 | #222432 | #2E3E64 (파랗게) | #1B1D28 (색조 그대로, 조금 어둡게) |

## 13. 키보드 규칙 실제 키 시험 (Karabiner 종료 뒤, 2026-11-12)

Karabiner 를 끄고 Hanmium 이 사용자 규칙 10개(조작 41개)로 키를 바꾸게 한 뒤 `Tools/live-keys.sh` 로 돌렸습니다.

**시험 방법**
- 시험 키는 실제 키보드와 같은 HID 단계로 보내고, Hanmium 이 바꾼 결과는 세션 단계에서 기록한 뒤 버립니다. 그래서 앱(Claude Code 등)에는 아무것도 닿지 않습니다.
- 맨 뒤 탭은 앱까지 새어 나간 시험 키를 세는데, 0개였습니다.
- 사용자의 진짜 입력이 섞인 항목은 다시 합니다.

| 항목 | 결과 |
|---|---|
| 일반 글자, ⌘C·⇧H·⌥A·⌥⇧H·⇧Tab·⌃Tab | 확인됨: 그대로 지나감 |
| ₩ 짧게 / 1.3초 혼자 누르고 떼기 | 확인됨: ₩ / 아무것도 안 나옴 (Karabiner 와 같음) |
| ₩+hjkl, ₩+j 꾹 | 확인됨: ← ↓ ↑ →, 반복 입력은 ↓ 반복 |
| ₩+Space+hjkl, +⇧ | 확인됨: ⌥화살표 / ⌥⇧화살표 |
| ₩+Space 혼자 | 확인됨: Space |
| [임시 진단] ₩+Space+왼⇧+; | 확인됨: 9 |
| ₩+Tab | 확인됨: Tab |
| ₩+⌥h·⌥l | 확인됨: 왼쪽·오른쪽 클릭 |
| ₩+⌥k·⌥j | 확인됨: 휠 위·아래 (0.35초에 약 410px) |
| ⌥+hjkl | 확인됨: 0.4초에 약 500pt 씩 네 방향 |
| Tab | 확인됨: 라벨이 열리고 다시 Tab 으로 닫힘 |
| ⇧+NumLock | 확인됨: 마우스 모드 켜기·끄기 |
| 마우스 모드: 숫자 패드 8 2 4 6 | 확인됨: 포인터 |
| 마우스 모드: 5 · / · * · - | 확인됨: 클릭(빠르게 두 번이면 더블클릭) |
| 마우스 모드: 7·1 / 9·3 / 0·. | 확인됨: Home·End / 휠 / 뒤로·앞으로 버튼 |
| 마우스 모드를 끈 뒤 | 확인됨: 숫자 패드가 원래 숫자로 돌아옴 |
| 이벤트 시각 단위 | 확인됨: `CGEvent.timestamp` 는 나노초(`CLOCK_UPTIME_RAW` 와 같음). 1초 같은 규칙 시간 계산이 맞음 |

- **처음 돌렸을 때 실패:** 마우스 모드가 이미 켜져 있었고, 포인터 시작점을 화면 가운데로 옮기기 전에 쟀습니다. 둘 다 시험 도구 문제였습니다. 지금은 시작할 때 숫자 패드 7 로 상태를 보고(Home 이 나오면 켜짐) 끄며, 끝날 때도 끕니다.
- **실제 손으로 누른 키는 확인 못 함:** 외장 키보드의 NumLock 키가 보내는 신호는 직접 확인하지 않았습니다.

  - Hanmium 은 웹의 스크롤 상자를 클래스 이름(`overflow-y-auto` 등)으로 알아봅니다.

  `ScrollFixtures` 페이지처럼 `role="region"` 과 `class="overflow-y-auto"` 를 달자 두 영역을 찾았습니다. 번호를 골랐다는 로그도 `라벨에서 n번 → 영역` 줄만 세게 고쳤습니다. 전에는 예전 WezTerm 시간 기록 줄과 잘못 맞았습니다.
- **처음 돌렸을 때 실패 2 — Hanmium 버그:** 라벨에서 k 를 짧게 누르면 스크롤 모드만 열리고 움직이지 않았습니다. 스크롤 모드가 뜰 때 키를 이미 뗐으면 이어 누르기를 하지 않았기 때문입니다. 손을 떼는 시점에 따라 움직이기도 하고 안 움직이기도 했습니다.
  - 고친 것: 이미 뗐으면 스크롤 모드에서 짧게(0.08초) 누른 것처럼 옮깁니다 (`ScrollMode.tapPress`).

## 15. 아직 확인하지 않은 것

- **스크롤 모드 Enter의 일반 앱 경로:** 링크·버튼이 아닌 자리를 찾아 누르기. VS Code, Slack 등에서 실제로 눌러 보지 않음 (WezTerm 경로만 확인).
- **물방울 이동 중 실시간 굴절:** 이동하는 동안 계속 다시 캡처. 실제 화면에서 보지 않음.
- **설정 창 전체:** 유리 슬라이더, 미리보기, 모양·영역 이동 선택, 영역 이동 속도, 터미널 휠 줄 수 입력란, 앱별 사용, 테두리 색, 기본값 복원, 내보내기·가져오기 버튼. 설정 창을 열어 보지 않음.
- **메뉴 막대 "앱 점검…" 결과 창:** 점검 내용은 `--check`로 확인했지만, 결과 창은 띄워 보지 않음.
- **물방울 이동 중 연속 캡처로 바뀌는 굴절:** 실제 움직임을 눈으로 보지 않음.
- **GPU를 쓸 수 없을 때 CPU로 돌아가는 경로:** 이 Mac에는 GPU가 있어서 확인하지 않음.
- **실제 라벨 모드의 유리 라벨:** 라벨이 수백 개일 때 처음 그리는 속도. 라벨 하나에 0.3ms로 추정.
- **화면 환경:** 여러 모니터, Retina 화면(이 Mac은 1920×1080, 1배).
- **WezTerm 탭이 여러 개인 창:** 탭 바 높이를 추정에 의존.
- **스크롤 모드 이어 쓰기 중 메뉴 기다리기:** VS Code 의 `...` 메뉴는 웹으로 그린 메뉴(`role="menu"`)이고 창이 포커스를 잃으면 닫힌다는 것은 VS Code 코드에서 확인. 메뉴가 열려 있으면 닫힐 때까지 스크롤 모드를 미루는 동작은 실제 VS Code 에서 눌러 보지 않음.

## 다시 확인하는 방법

**한 번에 전부**

```sh
Tools/run-all-tests.sh          # 화면·키보드를 건드리지 않는 시험 전부 (2~3분)
Tools/run-all-tests.sh --live   # 실제 키 시험까지: live-keys → live-modes → e2e-wezterm (키보드·마우스에서 손을 떼고)
```

실제 키 시험은 실행 중인 Hanmium.app 을 시험합니다. 고친 뒤에는 `./build.sh` 로 설치하고 다시 띄워 두고 돌립니다.

**회귀 테스트 (`Tools/`)**

```sh
Tools/check-apps.sh                       # 실행 중인 앱 전부 점검, 경고 있으면 종료 코드 1

Tools/e2e-wezterm.sh                      # 시험용 WezTerm 창에서 Enter·Esc 시나리오 (build.sh 후 앱을 다시 띄워 두고)
Tools/scroll-fixtures.sh                  # 웹 스크롤 영역 회귀 테스트 (시험 페이지마다 기대한 영역만 찾는지)
Tools/wezterm-fixtures.sh                 # WezTerm 패널 배치 회귀 테스트 (화면을 건드리지 않음, 20초쯤)

```

라벨 클릭 대상과 스크롤 영역 목록을 출력하고, 포커스가 있는 영역에는 `← 포커스`가 붙습니다.

**동작 로그**

스크롤 모드를 열고 닫을 때와 Enter를 누를 때마다, 찾은 영역·포커스·기억된 영역·시작 영역을 `~/Library/Logs/Hanmium.log`에 남깁니다. 1MB가 넘으면 새로 씁니다.

**시험 도구 ① 화면 구석 시험 패널**

`Sources/Hanmium`에서 `main.swift`만 뺀 파일들에 시험용 `main.swift`를 붙여 `swiftc`로 빌드합니다. 키 포커스를 받지 않는 `.nonactivatingPanel`을 화면 구석에 띄우고, `screencapture -R`로 찍은 뒤 끝냅니다. 터미널(WezTerm)에 화면 기록 권한이 있어서 캡처가 됩니다.

**시험 도구 ② 시험용 WezTerm 창에서 실제 키 입력**

쓰고 있는 창은 건드리지 않습니다. 5초 정도 걸리고, 그동안 키보드를 쓰지 않아야 합니다.

```sh
P1=$(wezterm cli spawn --new-window -- bash -c 'seq 1 3000; exec bash')
P2=$(wezterm cli split-pane --pane-id $P1 --right --percent 30 -- bash -c 'seq 1 3000; exec bash')
wezterm cli activate-pane --pane-id $P1; sleep 1.2
# 앞 창이 시험 창("wezterm-gui, bash")인지 먼저 확인한 다음에만 키를 보낸다
osascript -e 'tell application "System Events" to tell (first process whose frontmost is true) to get {name, value of attribute "AXTitle" of front window}'
osascript -e 'tell application "System Events" to key code 38 using {shift down, command down}'  # ⇧⌘J 열기
osascript -e 'tell application "System Events" to key code 48'                                   # Tab
osascript -e 'tell application "System Events" to key code 36'                                   # Enter
screencapture -x /tmp/hanmium-check.png
wezterm cli kill-pane --pane-id $P2; wezterm cli kill-pane --pane-id $P1
cat ~/Library/Logs/Hanmium.log
```

**가려진 창의 위치 확인**

`screencapture -x -o -l <CG 창 번호>`는 다른 창에 가려진 창도 그 창만 찍습니다. 계산한 영역 사각형을 그 위에 그려 비교합니다.

## 테스트할 때 주의

- **합성 클릭 전 확인:** 누르려는 창이 맨 위인지 같은 명령 안에서 확인합니다. 예전에 잘못된 클릭으로 VS Code에 탭이 열린 적이 있습니다.
- **Claude Code 패널은 스크롤하지 않음:** 휠이 화살표 키로 바뀌어 입력창이 바뀝니다.
- **Esc를 함부로 보내지 않음:** 모드가 실제로 열렸을 때만 보냅니다. 열리지 않았으면 Esc가 사용 중인 앱으로 갑니다.
- **새 창이나 시험 패널은 짧게:** 띄우는 동안 사용자 입력이 그쪽으로 갈 수 있습니다.
